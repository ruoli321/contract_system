# B5 业财一体化 · 理解阐述与方案设计文档

**方案主题：以合同为源头的"合同 → 应收应付 → 收付款核销 → 经营台账"数据闭环设计**

> 适用系统：合同管理系统（Odoo 17 `contract_ai` 模块 + FastAPI AI 微服务）
> 对照评分项：B5 业财一体化（3 分）—— "口头/文档层的正确理解 + 方案设计"（1.5 分）

---

## 一、核心理念阐述：为什么"合同是业财一体化的依据"

### 1.1 合同的双重属性

合同在企业经营管理中同时是**业务凭证**（约定买什么、卖什么、何时交付）和**财务凭证**（约定付多少、何时付、怎么付）。传统信息化的痛点在于两个属性被割裂：业务系统管签约归档，财务系统手工建应收应付台账，两套数据靠人工对账，产生口径不一、逾期失控、核销脱节等问题。

业财一体化的本质，就是让**同一份合同成为业务流与资金流的共同事实来源（Single Source of Truth）**——财务侧的应收应付不是财务人员"另建一套账"，而是从合同中的收付款节点**自动派生**。

### 1.2 三层递进理解

| 层次 | 理解 | 含义 |
|---|---|---|
| **合同是计划源** | 合同中的收付款节点（预付/到货/分期/尾款）是业务履约节奏的**货币化表达**，它定义了资金流"应该何时发生、发生多少" | 业务事件驱动财务计划 |
| **合同是派生源** | 应收应付记录由合同节点**自动生成**，方向、金额、日期均可从合同类型与条款推导，杜绝二次录入 | 单一事实来源，数据同源 |
| **合同是闭环锚点** | 每笔收付款核销必须**回写**合同与计划，合同台账因此实时反映履约进度，反过来监控业务（逾期预警、剩余待执行、归档条件） | 财务结果回写业务，形成闭环 |

### 1.3 数据闭环一句话表述

> **合同生效（业务事件）→ 派生收付款计划（应收应付）→ 到期提醒驱动执行 → 收付款核销（财务动作）→ 回写合同汇总与经营台账（数据回流）→ 逾期/进度反哺业务管理（监控闭环）。**

## 二、总体方案架构：四层数据模型

```
┌─────────────────────────────────────────────────────────────┐
│  L1 合同层（业务事实）                                        │
│  contract.contract：合同金额/类型/状态机/draft→approval→seal   │
└──────────────────────────┬──────────────────────────────────┘
                           │ 合同生效触发节点实例化
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  L2 计划层（应收应付）                                        │
│  contract.payment.plan：节点类型/方向自动判定/计划金额·日期     │
│  来源标记：AI 提取生成 / 人工录入                              │
└──────────────────────────┬──────────────────────────────────┘
                           │ 到期驱动执行 → 核销回写
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  L3 执行层（收付款核销）                                      │
│  actual_amount / actual_date / 结算方式                      │
│  状态机：draft→confirmed→partial→paid（核销完成）             │
└──────────────────────────┬──────────────────────────────────┘
                           │ store compute 汇总上卷
                           ▼
┌─────────────────────────────────────────────────────────────┐
│  L4 台账层（经营台账）                                        │
│  合同级：planned/paid/remaining/overdue_count                │
│  台账视图：列表 + Pivot + Graph + Excel/PDF 导出 + 逾期提醒    │
└─────────────────────────────────────────────────────────────┘
```

四层之间的连接全部是**系统自动流转**（触发器/compute/定时任务），无人工二次录入环节——这正是"合同驱动"与"人工台账"的本质区别。

## 三、业务流程设计（端到端）

### 阶段 1：合同起草与节点识别（业务 → 数据）

| 项 | 说明 |
|---|---|
| 触发者 | 合同经办人 |
| 入口 | ① 手工新建合同并录入收付款节点；② 上传 PDF → AI 服务提取付款条款 |
| 系统动作 | AI 返回结构化 JSON（节点名称/类型/金额/日期），自动生成 `contract.payment.plan`，`source="ai_extracted"`；**重新提取时仅覆盖 AI 来源计划，人工计划不受影响** |
| 输出 | 合同详情页"收付款计划"Tab 出现待确认计划（草稿态） |

### 阶段 2：审批与用印生效（核心触发节点）

| 项 | 说明 |
|---|---|
| 触发者 | 审批人 → 用印人 |
| 状态机 | `draft → approval → seal` |
| 系统动作 | 合同到达 **seal（已用印）** 即为法律意义上的资金义务成立时点，此时计划从"草稿"转入"已确认"（confirmed），进入执行队列 |
| 业务含义 | **用印 = 应收应付正式立账**，这是业务事件触发财务流程的关键闸口 |

### 阶段 3：应收应付执行队列（计划管理）

- 应收应付自动分方向：**采购/租赁 → 应付（我方付款）；销售/服务/咨询 → 应收（我方收款）**，由系统按合同类型自动判定，无需人工标注
- "收付款台账"菜单提供全公司视角的执行队列：按到期日排序、按方向/状态分组、Pivot 多维分析
- 定时任务（cron）每日扫描：临期计划 → chatter 提醒经办人；逾期计划 → 标记 `is_overdue` 并进入合同级 `overdue_count`

### 阶段 4：收付款执行与核销（财务动作）

| 项 | 说明 |
|---|---|
| 触发者 | 财务/经办人 |
| 动作 | 登记实际金额 `actual_amount`、实际日期 `actual_date`、结算方式 |
| 核销规则 | 实际金额 = 计划金额 → 状态 `paid`（全额核销）；实际金额 < 计划金额 → 状态 `partial`（部分核销，剩余金额自动计算 `remaining_amount`）；补足后可再次核销至 `paid` |
| 校验 | 计划金额必须 > 0；已完成计划禁止回退草稿，防止核销数据被篡改 |

### 阶段 5：回写与台账上卷（数据回流）

- 每次核销动作实时上卷合同级汇总字段（存储型 compute，自动重算）：

```
planned_amount_total   = Σ 计划金额          （合同盘子）
paid_amount_total      = Σ 实际核销金额      （已执行）
remaining_amount_total = planned − paid     （剩余待执行）
overdue_count          = Σ 逾期计划数        （风险敞口）
```

- 合同"计划总额 vs 合同金额"可自动校验（计划覆盖率 = planned / amount），发现节点漏录

### 阶段 6：监控、归档与对账（闭环收口）

- 逾期提醒 cron：逾期未核销计划 → 合同 chatter 留痕提醒
- 到期归档 cron：已用印且失效日期已过的合同自动 `archived`；**归档前校验剩余待执行金额**，避免带账归档
- 台账输出：Excel 导出（明细 + 按类型汇总分析双 Sheet）、PDF 报表（含收付款计划表与汇总行），直接服务经营分析会与对账场景

## 四、数据流转逻辑

### 4.1 节点 → 计划的字段映射

| 合同/AI 提取信息 | 计划字段 | 说明 |
|---|---|---|
| 节点名称（"预付款 30%"） | `name` | 收付款节点 |
| 节点性质 | `milestone` | 预付/到货验收/完工验收/分期/尾款 |
| 金额或比例×合同金额 | `planned_amount` | 计划金额（币种继承合同） |
| 约定支付时点 | `planned_date` | 计划日期 |
| 条款正文 | `description` | 支付条件/验收标准 |
| 合同类型 | `direction`（compute） | 采购/租赁→应付；销售/服务→应收 |
| 提取方式 | `source` | ai_extracted / manual（覆盖策略依据） |

### 4.2 状态流转矩阵（合同 × 计划联动）

| 合同状态 | 对计划的影响 |
|---|---|
| draft / approval | 计划允许草稿态增删改（节点待定） |
| **seal（用印）** | 计划批量 `confirmed`，应收应付正式立账 |
| archived / void | 计划冻结新增；作废合同计划批量 `cancelled` |
| 任意状态 + 核销动作 | 仅影响计划自身状态，实时上卷合同汇总 |

计划自身状态机：`draft → confirmed → partial → paid`，旁路 `cancelled`（可从 draft/confirmed/partial 进入，不可从 paid 进入）。

### 4.3 金额守恒与一致性设计

- **行级**：`remaining_amount = planned_amount − actual_amount`（存储 compute）
- **合同级**：四个汇总字段 `store=True` + `@api.depends`，核销写入即触发重算，台账查询零延迟
- **方向维度**：台账可按 `direction` 拆分应收侧/应付侧两个口径，分别对应 AR/AP 视角

## 五、关键节点定义

| 编号 | 节点 | 触发条件 | 系统动作 | 数据写入 | 下游影响 |
|---|---|---|---|---|---|
| **N1** | AI 提取完成 | PDF 识别接口返回 | 生成/覆盖 AI 来源计划 | plan(source=ai_extracted) | 合同页展示待确认计划 |
| **N2** | **合同用印生效** ★ | state → seal | 计划批量确认立账 | plan.state=confirmed | 进入应收应付执行队列 |
| **N3** | 到期提醒 | cron 每日扫描 planned_date 临期 | chatter 提醒经办人 | 无状态变更 | 催办执行 |
| **N4** | 逾期判定 | planned_date < today 且无 actual_date | 标记逾期 | is_overdue=True → overdue_count | 风险敞口可视 |
| **N5** | **核销登记** ★ | 财务登记 actual_amount/date | 行级核销（全额/部分） | actual_*、state=paid/partial | 触发合同汇总重算 |
| **N6** | 全额核销完成 | remaining_amount = 0 | 计划终态 paid | state=paid | 可判断合同资金义务履约完毕 |
| **N7** | 合同归档 | 失效日期已过（cron） | 自动 archived | state=archived | 台账进入历史口径 |

N2（合同生效驱动立账）与 N5（核销回写台账）是"合同驱动业财一体化"的两个枢纽节点——前者保证**业务事件触发财务流程**，后者保证**财务结果回流业务台账**。

## 六、系统交互说明

### 6.1 模块内交互（Odoo 侧）

- **状态机驱动**：合同按钮动作（提交审批/用印/归档/作废）串联计划批量状态变更
- **compute 数据链**：plan 行写入 → `@api.depends` 自动上卷 contract 汇总 → 台账视图/报表实时反映
- **约束保护**：金额正数校验、paid 不可回退、归档校验剩余待执行

### 6.2 与 AI 微服务交互（FastAPI 侧）

```
Odoo（上传 PDF）──HTTP POST /api/extract──▶ AI 服务（pdfplumber/PaddleOCR + LLM）
Odoo ◀────结构化 JSON（分类/条款/付款节点）────┘
       └→ 按节点 JSON 生成 plan（ai_extracted）
       └→ 重新提取仅覆盖 AI 来源，人工数据零丢失
```

AI 服务独立部署（docker-compose 编排，`AI_SERVICE_URL` 注入），通过 HTTP 松耦合交互，AI 能力升级不影响业财数据链路。

### 6.3 定时任务交互

| Cron 任务 | 频率 | 作用 |
|---|---|---|
| 收付款逾期提醒 | 每天 | 扫描逾期计划 → chatter 提醒，驱动核销 |
| 合同到期自动归档 | 每天 | 扫描过期合同 → 自动归档，收口闭环 |

### 6.4 与 Odoo 标准财务模块对接（深化路线设计）

当前收付款核销在合同域内完成（轻量闭环）。如需进入总账，设计映射如下：
                       
- `direction=receivable` 的核销 → 派生 `account.move`（借：应收账款 / 贷：主营业务收入+销项税）
- `direction=payable` 的核销 → 派生（借：库存/成本+进项税 / 贷：应付账款）
- plan 增加 `account_move_id` 回写字段，保证合同域与会计域双向可溯
- 该层为**可选增强**，不改变"合同 → 计划 → 核销 → 台账"的核心闭环

### 6.5 报表输出交互

- Excel 台账导出：明细 Sheet（17 列含计划数/逾期数/AI 来源）+ 汇总分析 Sheet（按类型统计已完成占比）
- PDF 报表：合同详情含收付款计划表与计划/已完成/剩余汇总行
- Pivot/Graph：按类型 × 状态多维分析金额

## 七、方案实现度对照与深化路线

| 评分要求的闭环环节 | 系统现状 |
|---|---|
| 从合同提取付款节点 | ✅ AI 提取 + 人工录入双通道，来源标记与覆盖策略 |
| 自动生成收付款计划 | ✅ 节点→计划字段映射、方向自动判定、状态机 |
| 台账联动 | ✅ 合同级四项汇总自动上卷、台账视图/Pivot、Excel+PDF 输出 |
| 逾期监控 | ✅ is_overdue 计算 + cron 逾期提醒 |
| 收付款核销 | 🟡 行级核销（actual_amount/date + partial 状态）已有，可增强批量核销/核销流水表 |
| 应收应付立账 | 🟡 计划确认即立账（合同域内），可深化对接 account 模块生成会计凭证 |
| 经营台账 | ✅ 收付款台账 + 汇总分析；可扩展按期间的经营看板 |

**深化路线**：

- **P1** 核销流水表（每笔核销留痕可冲销）+ 批量核销
- **P2** 对接 `account.move` 生成正式会计凭证
- **P3** 按月度经营台账看板（应收账龄/应付账龄分析）
